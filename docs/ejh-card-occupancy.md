# 银行卡类型与 EJH 单卡占用

## 配置入口

- Pro 管理 → 银行卡信息：类型列显示 EJH / 其他，新增和编辑可选择类型。
- EJH 卡台 → 配置与模板 → 接口设置：一卡同时一个号，默认开启，保存后生效。
- 升级时已有卡及历史订单默认归为其他，不根据卡名或来源猜测。需要纳入 EJH 管理的旧卡可手动修改类型；EJH 接口新开的卡自动归为 EJH。

类型与真实卡台来源分别保存。同一卡号的重复记录共用类型、累计开通数和占用状态。手动添加的 EJH 类型卡没有卡台订单绑定时，仅管理本地记录，不能查询卡台余额或执行资金操作。

## 占用规则

手动开通、手动启动全自动和定时自动开通都经过同一数据库检查。开始自动登录前预占；提交付款前将预占原子转换为持久化订单占用。

- 开通成功、合并成功、停止任务、删除账号/卡片、刷新余额均不释放成功订单的占用。
- 只有自动识别回款后才释放成功订单的占用；移出完成或 team_removed 均继续占用。授权撤销（类型 2，状态 1/2）和已入账普通退款（类型 5/16，状态 2）计入回款；销卡退余额不计入。
- 未提交付款的登录失败、明确失败的付款可释放；超时、未知、处理中保留占用，须核实原订单。
- 累计最大开通数保持原规则，回款不清零。
- 关闭开关不删除占用历史；重新开启只拦截新准入，关闭期间已经预占的任务可以继续，全部旧占用释放后才接受新账号。
- 运行中的 EJH 卡不可改为其他或替换卡号；不影响普通卡原有容量规则。

EJH 页面只展示 EJH 类型卡的账号回款、流水、相关操作和统计；Pro 银行卡的关联账号列表保留两种类型的数据。卡台账户余额仍是供应商账户总额，不是卡片余额之和。

## 持久化与部署边界

选卡、补卡、预占已串行化，避免手动、全自动、定时任务同时抢到同一空闲卡。重复提交保留原订单和原选卡参数，不重复开卡或付款。

## 无可用卡时补卡（2026-10-15）

- Pro 管理 → Pro 全自动配置 → 银行卡与补卡：开启「无可用卡时自动从 EJH 开卡」，选择模板并保存每日数量和金额预算。手动单项开通、全自动、定时任务共用选卡与预占入口。
- 自动选卡优先复用现有可用卡；没有可用卡时才购买新 EJH 卡。被占用的 EJH 卡即便还有累计名额也不可复用；之前选中的 EJH 卡被其他任务抢先占用时，在自动补卡已启用的前提下重新选卡／补卡。
- 关闭自动补卡时不买卡；每日预算、未核实开卡、卡片状态及定时任务的最大未合并数保护保持有效。单项手动开通不改变既有定时容量策略。
- 一卡累计上限 4 与一卡同时一号分别计算：回款后释放占用但不清零累计数。EJH 默认上限独立于普通银行卡全局上限，需在 EJH 卡台设置为 4，或设置单卡上限为 4。
- 风控订单类别 supportedMccGroup 按官方文档显示 flight（机票）、hotel（酒店）、ecom（跨境电商）、trv（非酒店机票）。只修正标签，不擅自修改已有模板保存值。

SQLite 内以实体卡号摘要标识，付款准入在写事务中加锁。订单占用及逐笔释放记录跨重启保留；迁移文件携带类型与逐笔回款确认标记；旧文件仅有移出释放标记时不能据此释放 EJH 占用。

两个独立部署、各自独立数据库之间不共享占用锁。同一张实体卡不要同时分配到两套独立运行的系统；跨系统全局互斥需要共享协调服务，不属于本次改动。

升级前备份整个 data 目录；前端资源内嵌于 Go 程序，更新后需重新构建并重启服务。
